## 2. Анализ экзамена

**[ДЭ]** Шифр варианта: **В2_КОД 09.02.07-3-2026-ПУ**, вариант № 2, профильный уровень, ГИА.

### Модуль 1 — Проектирование и разработка информационных систем (1 ч 30 мин)

**[ДЭ]** Предметная область — портал **«Конференции.РФ»**: бронирование помещений для всероссийских конференций. Типы помещений: **аудитория, коворкинг, кинозал**.

Требования:

1. Проектирование и создание структуры БД: таблицы с типами полей и связями. **Особое внимание — ER-диаграмме.**
2. Интерфейс по современным стандартам фронтенда и бэкенда, **с ООП** и **библиотекой стилей**.
3. Репозиторий системы контроля версий, **минимум три коммита** перед каждым новым этапом.
4. **Регистрация**: обязательны все поля — логин, пароль, ФИО, телефон, e-mail. Логин **уникальный, латинские буквы и цифры, минимум 6 символов**; пароль — **8 и более**. После успешной валидации — запись в БД.
5. **Вход** по паре логин-пароль; при неудаче — информативные уведомления; ссылка с текстом **«Еще не зарегистрированы? Регистрация»** и обратная ссылка на странице регистрации.
6. **Личный кабинет**: история своих заявок + отзывы о полученных услугах.
7. **Страница оформления заявки**: помещение, дата начала конференции, способ оплаты — запись в БД, отправка администратору.
8. **Админка**, защищённая логином **`Admin26`** и паролем **`Demo20`**: просмотр всех заявок, смена статуса. Начальный статус — **«Новая»**, допустимые дальнейшие — **«Мероприятие назначено»**, **«Мероприятие завершено»**.

Приложения: `Прил_В2_КОД 09.02.07-3-2026-М1.zip` (содержимого в материалах нет — **[ПЛАН]** советует открывать архивы первым делом).

### Модуль 2 — Разработка дизайна веб-приложений (1 ч 30 мин)

**[ДЭ]**

- Авторизация: предупреждения при неверном логине или пароле.

## 4. Пробелы

Что в **[ПЛАН]** упомянуто вскользь или отсутствует, хотя нужно на экзамене:

1. **Точные формулировки.** «Еще не зарегистрированы? Регистрация», `Admin26`/`Demo20`, три статуса — баллы теряются именно на буквах. В платформе сделана отдельная проверка дословных значений с автотестами на точное совпадение строк.
2. **Порядок первых 10 минут экзамена.** Появляется только на неделе 30. Платформа даёт чек-лист старта в экзаменационном режиме.
3. **Отсутствие критериев оценивания в [ДЭ].** Платформа строит собственную модель оценки на основе пересчёта пунктов задания (см. раздел 7), явно помечая её как **[РЕШЕНИЕ]**.
4. **Работа без интернета внутри тренажёра.** Если платформа тянет CDN, тренироваться офлайн нельзя. Все ассеты (Monaco, WASM SQLite, шрифты) лежат локально.
5. **Проверка ER-диаграммы.** Автоматически картинку не проверить. Платформа проверяет схему БД по DDL (`CREATE TABLE` исполняется в SQLite-песочнице, проверяются таблицы, типы, ключи, связи), а сама диаграмма выносится в чек-лист ручной самопроверки — это честно помечено как ручной шаг.
6. **Отзыв «только после смены статуса»** — правило легко забыть; в программе оно одна строка. Вынесено в отдельные задания и в критерии экзаменационного чек-листа.

## 5. Предлагаемый стек

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | **Next.js 16 (App Router) + React 19 + TypeScript** | Прямо рекомендован ТЗ (раздел 7). Один проект вместо двух, серверные компоненты уменьшают клиентский JS (раздел 34 ТЗ), встроенный code splitting |
| Стили | **Tailwind CSS 4** | Рекомендован ТЗ. Нет рантайма, вся стилизация в сборке — хорошо для офлайна и производительности |
| Компоненты | Собственные примитивы в `components/ui` | shadcn/ui — генератор, который тянет файлы из сети; локально пишем те же по смыслу примитивы без внешней зависимости |
| Редактор | **Monaco Editor** (локальная копия в `public/vendor/monaco`) | Рекомендован ТЗ. Копируется из `node_modules` скриптом — работает офлайн |
| БД | **SQLite через Prisma** (переключение на PostgreSQL — одна строка в `schema.prisma`) | ТЗ рекомендует PostgreSQL + Prisma. Prisma взята; СУБД по умолчанию SQLite, потому что платформа должна запускаться на учебном ноутбуке без установки сервера БД и без интернета |
| Аутентификация | **bcryptjs + JWT (jose) в httpOnly-cookie** | ТЗ разрешает «другой современный безопасный механизм». Дополнительный плюс: это ровно та связка, которую студент обязан уметь писать на экзамене **[ПЛАН]**, то есть код платформы служит образцом |
| Запуск кода | **Песочница: iframe `sandbox="allow-scripts"` + Web Worker внутри него** | См. раздел 9 |
| SQL-тренажёр | **sql.js (SQLite, скомпилированный в WebAssembly)** | Реальное выполнение SQL в браузере без сервера БД. Отличия от MySQL обрабатываются слоем совместимости и показываются студенту |
| Графики | Recharts | Только там, где график действительно помогает (раздел 24 ТЗ) |
| Тесты | Vitest (unit + integration), Playwright (e2e) | Раздел 32 ТЗ |

**Честное замечание.** Платформа написана на Next.js, а студент учит Vite + Express. Это сделано намеренно: ТЗ платформы требует Next.js, а учебный стек воспроизводится **внутри заданий** (шаблоны кода, структура проекта, маршруты Express) — студент тренирует Express и Vite в задачах, а не в исходниках тренажёра.

## 6. Архитектура

```
Браузер (React 19, серверные компоненты Next.js)
   │
   ├── UI: dashboard / план / теория / задачи / проекты / экзамены / прогресс / повторение / поиск / админка
   │
   ├── Редактор Monaco (локальный)
   │
   └── Песочница выполнения кода
          iframe sandbox="allow-scripts" (opaque origin)
             └── Web Worker (для JS/TS) или прямой DOM (для HTML/CSS/React)
                    ↓ postMessage(результаты тестов)
   │
   ▼
Route Handlers / Server Actions (Next.js)
   ├── lib/grading      — подсчёт баллов за попытку
   ├── lib/progress     — статусы уроков, разблокировка, streak
   ├── lib/srs          — интервальное повторение
   ├── lib/recommend    — рекомендации и анализ готовности
   └── lib/content      — слой контента: файлы + переопределения из БД
   │
   ▼
Prisma → SQLite (по умолчанию) / PostgreSQL

Контент (не в коде компонентов):
content/curriculum, content/theory, content/tasks, content/quizzes, content/projects, content/exams
```

**Ключевое решение [РЕШЕНИЕ]:** контент лежит в типизированных файлах (`content/**`), а админ-панель пишет **переопределения** в таблицу `ContentOverride`. Слой `lib/content` склеивает файлы и переопределения. Это выполняет требование «контент обновляется без переписывания кода» (раздел 31 ТЗ), не превращая репозиторий в дамп БД.

## 7. База данных

Сущности из раздела 28 ТЗ, приведённые к реальным потребностям платформы.

**Контентные (в файлах, в БД только переопределения):** `Course → Month → Week → Day → Lesson → Topic`, `Task`, `TestCase`, `Quiz`, `Project`, `Exam → ExamTask`.

**Пользовательские (в БД):**

| Модель | Назначение |
|---|---|
| `User` | логин, хеш пароля, имя, роль, дата экзамена, настройки |
| `Progress` | статус любой сущности (`lesson`/`topic`/`task`/`project`/`exam`) для пользователя |
| `Submission` | попытка: код, язык, результат тестов, баллы, время, число подсказок |
| `QuizAttempt` | ответы на тест, баллы |
| `ExamAttempt` / `ExamTaskAnswer` | запуск экзамена, таймеры модулей, ответы, чек-лист, итог |
| `ReviewItem` | карточка интервального повторения: интервал, дата следующего повтора, лёгкость |
| `Achievement` / `UserAchievement` | достижения |
| `Note`, `Bookmark` | заметки и закладки пользователя |
| `StudySession` | дневная активность: минуты теории/практики, streak |
| `TopicStat` | агрегат по теме: попытки, успехи, подсказки, среднее время — источник списка слабых тем |
| `ContentOverride` | правки контента из админки |

Связи: `User 1—N Progress/Submission/…`; `Submission N—1 Task`; `ExamAttempt 1—N ExamTaskAnswer`; `ReviewItem N—1 Topic`; `TopicStat` уникален по паре (`userId`, `topicId`).

## 9. Система проверки кода

**Требование ТЗ (раздел 8):** пользовательский код нельзя запускать на сервере без изоляции.

**[РЕШЕНИЕ]** Код выполняется **только в браузере**, в двойной изоляции:

```
Страница задания
   └── <iframe sandbox="allow-scripts">          ← opaque origin: нет доступа
         │                                          к cookie, localStorage и DOM приложения
         ├── (JS/TS) new Worker(blob)            ← отдельный поток: бесконечный цикл
         │                                          не вешает интерфейс
         └── (HTML/CSS/React) прямой рендер в документ песочницы
```

Меры защиты:

| Требование ТЗ | Реализация |
|---|---|
| sandbox | `sandbox="allow-scripts"` без `allow-same-origin` — уникальный opaque origin |
| timeout | Родитель ставит таймер и уничтожает iframe/worker по истечении (по умолчанию 5 с) |
| защита от бесконечных циклов | Worker в отдельном потоке + принудительный `terminate()`; для DOM-задач — снос iframe |
| ограничение памяти | Жёсткий лимит браузер не даёт; ограничение достигается уничтожением контекста по таймеру. Ограничение описано честно, а не имитируется |
| файловая система | В браузере недоступна |
| сетевой доступ | `fetch`, `XMLHttpRequest`, `WebSocket`, `importScripts`, `EventSource` перекрыты заглушками, бросающими ошибку |
| системные команды | Недоступны: нет Node API |
| безопасное завершение | Уничтожение iframe освобождает и worker, и таймеры |

**Как проверяются задания:** не сравнением текста, а исполнением тест-кейсов (раздел 14 ТЗ): каждое задание описывает набор тестов с входом и ожидаемым результатом; песочница вызывает решение и возвращает фактические значения, время выполнения и ошибки. Для DOM-задач тест — функция-ассерт над документом песочницы. Для SQL — сравнение таблиц результата в SQLite (WASM).

### Что нашёл финальный аудит и что исправлено

Аудит (`e2e/audit.spec.ts`) прошёл по всем страницам платформы. Найденное
исправлено, а проверки оставлены в наборе тестов, чтобы это не вернулось:

1. **Шапка уезжала за край на 390 px** — у растягивающейся ссылки поиска не
   было `min-width: 0`, и группа кнопок справа выходила за экран на 39 px.
2. **Широкая таблица в теории тянула за собой всю страницу** — контейнер с
   прокруткой не был ограничен по ширине.
3. **Колонки «так не надо / а так правильно»** растягивались по ширине кода
   внутри: гриду не хватало `min-w-0` у ячеек.
4. **Мелкие цели нажатия** — кнопки выхода и закрытия меню были 27–30 px,
   чип-ссылки 25 px. Приведены к 32 px и больше.
5. **Редактор кода не представлялся скринридеру** — Monaco прячет внутри
   обычное текстовое поле, и без `ariaLabel` оно читалось как безымянное.
6. **Расхождение баллов у 26 заданий** — `maxScore` не совпадал с суммой
   баллов тестов, из-за чего прогресс считался неверно. Приведено в
   соответствие, проверка добавлена и в валидатор, и в тесты.
7. **Ссылка на несуществующую тему** `express-routes` в четырёх требованиях
   экзамена — исправлена на `express-basics`.

### Чего в платформе намеренно нет

Перечислено, чтобы не создавалось впечатления, будто это забыли:

- **Серверного исполнения кода.** Всё выполняется в браузере: серверная
  песочница потребовала бы Docker и постоянно работающего сервера, а
  платформа должна запускаться одной командой и работать офлайн.
- **Проверки проекта студента.** Платформа не имеет доступа к его
  репозиторию, MySQL и запущенному приложению. Соответствующие пункты
  честно помечены как ручные и считаются отдельной суммой.
- **Официальной шкалы оценивания.** Её нет в задании. Веса требований —
  обоснованное **[РЕШЕНИЕ]**, разобранное в [`GRADING.md`](./GRADING.md).
- **Других официальных вариантов экзамена.** Источник один — вариант № 2.
  Всё остальное помечено как авторское (**[РЕШЕНИЕ]**).
