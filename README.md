# Подготовка к демоэкзамену 09.02.07

Интерактивная платформа подготовки к демонстрационному экзамену по специальности
**09.02.07 «Информационные системы и программирование»**, квалификация
*Разработчик веб и мультимедийных приложений*.

Платформа построена на двух реальных источниках и ни на чём больше:

| Источник | Что из него взято |
|---|---|
| `plan_podgotovki_DE_09.02.07.md` — 7-месячная программа подготовки | Учебный план: 7 месяцев, 30 недель, 210 дней. Разобран скриптом, а не переписан руками |
| `V2_KOD_09_02_07-3-2026-PU.pdf` — задание демоэкзамена, вариант № 2 | Требования экзамена с дословными формулировками, регламент трёх модулей, режим «ДЕМОЭКЗАМЕН» |

Оба источника — учебные материалы колледжа, поэтому самих файлов в репозитории нет.
Всё, что платформа из них берёт, уже лежит в коде: план — в
`content/curriculum/plan.generated.json`, требования экзамена с дословными цитатами —
в `content/exams/`. Скрипт `scripts/parse-plan.mjs` понадобится только тому, у кого
исходный `.md` есть локально.

Разбор источников со ссылками на каждое утверждение — в [`docs/ANALYSIS.md`](./docs/ANALYSIS.md).

## 1. Что это и зачем

**Цель.** Довести студента от нуля до состояния, в котором он за четыре часа
собирает работающее веб-приложение с базой данных, регистрацией, ролями и
админкой — то есть до того, что требует демоэкзамен.

**Задачи платформы:**

- разложить 7-месячную программу по дням и вести студента по ней;
- дать теорию, практику с реальным выполнением кода и проверку знаний;
- показывать честную картину прогресса и называть слабые места;
- тренировать режим экзамена: три модуля, таймер, чек-лист требований;
- готовить к смене предметной области — на экзамене может попасться другой
  вариант задания.

**Ключевой принцип.** Платформа не выдумывает содержание экзамена. Всё, что
взято из источников, помечено; всё, что решил разработчик платформы, помечено
отдельно и объяснено. См. [`docs/GRADING.md`](./docs/GRADING.md).

## 2. Возможности

### Учебный процесс

- **Учебный план** — 210 дней, разобранных из программы: теория, практика,
  контрольные дни, повторения. У каждого дня есть своё практическое задание.
  Открытие материала не запирает отстающих.
- **Теория** — 104 темы: краткая суть, «что необходимо знать», подробный разбор,
  примеры кода, типичные ошибки с объяснением причины.
- **Практика** — 210 заданий с реальным выполнением кода в пяти средах и
  1280 тест-кейсами: **по заданию на каждый день плана**, включая дни
  повторения, контрольные и выходные. Оценка — по пройденным тестам,
  а не по совпадению текста. Седьмой день каждой недели — сборка:
  задание, в котором нужно применить всё, что появилось за неделю.
- **Тесты** — 104 теста, 520 вопросов шести типов: один ответ, несколько
  ответов, верно/неверно, сопоставление, последовательность, свободный ответ.
  К каждому вопросу — пояснение.
- **Мини-проекты** — 7 проектов (по одному на месяц) с ТЗ, требованиями,
  ограничениями, чек-листом, подсказками и частичной автопроверкой.
- **Интервальное повторение** — SM-2 с интервалами из программы: 2 → 5 → 10 → 21 день.

### Экзамен

- **Режим «ДЕМОЭКЗАМЕН»** — вариант № 2 с дословными формулировками задания:
  три модуля, отдельный таймер на каждый, 25 требований с цитатами.
- **Тренировочные варианты** — две другие предметные области, тот же каркас.
  Помечены как авторские: официальное задание одно.
- **Честное разделение оценки** — автоматически проверенное показывается
  отдельно от того, что студент отмечает в чек-листе сам.

### Обратная связь

- **Прогресс** — по месяцам, неделям, технологиям; процент успешности,
  среднее время, использованные подсказки.
- **Слабые темы** — с объяснением причины словами, а не только числом.
- **Рекомендации** — конкретные действия со ссылками, а не «молодец, продолжай».
- **Готовность к экзамену** — взвешенная оценка с раскрытием, из чего сложилась.
- **Достижения** и серия дней подряд.
- **Предэкзаменационный режим** — за 30 дней до экзамена отдельный план.

### Прочее

- Глобальный поиск по темам, заданиям, проектам.
- Горячие клавиши (`Ctrl+K`, `G` + буква, `Ctrl+Enter`).
- Тёмная тема, масштаб шрифта.
- Админка для правки контента без пересборки.
- Работа **без интернета**: все библиотеки локальные.

## 3. Технологический стек

| Слой | Технология | Почему именно она |
|---|---|---|
| Фреймворк | Next.js 16 (App Router) | Серверные компоненты и server actions: меньше клиентского кода |
| Язык | TypeScript 5.9 | Строгий режим, `any` в проекте нет |
| UI | React 19 + Tailwind CSS 4 | Быстрая вёрстка, темы через CSS-переменные |
| База | Prisma 6 + SQLite | Запуск без установки СУБД; переключение на PostgreSQL — одна строка |
| Вход | bcryptjs + JWT (`jose`) в httpOnly-cookie | Ровно то, что студент будет писать на экзамене |
| Редактор кода | Monaco Editor (локальная копия) | Тот же редактор, что внутри VS Code |
| SQL в браузере | sql.js (SQLite на WebAssembly) | Настоящий SQL без сервера |
| Графики | Recharts | Только там, где график действительно помогает |
| Тесты | Vitest + Playwright | Логика — модульно, браузер — по-настоящему |

Выбор стека объясняется в [`docs/ANALYSIS.md`](./docs/ANALYSIS.md), раздел 7.

## 5. Установка

```bash
git clone <адрес репозитория>
cd ExamPreparation
npm install
```

`npm install` автоматически выполняет `postinstall`:

1. `prisma generate` — генерирует клиент базы данных;
2. `node scripts/copy-assets.mjs` — копирует Monaco, sql.js, компилятор
   TypeScript и собирает React-бандл для песочницы в `public/vendor`.

Дальше — настройка окружения и базы (разделы 6 и 7).

Одной командой (после создания `.env`):

```bash
npm run setup
```

Она делает `prisma generate` → `db:push` → `db:seed` → `assets`.

## 6. Настройка `.env`

Скопируйте пример и заполните:

```bash
cp .env.example .env
```

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `DATABASE_URL` | Строка подключения к базе | `file:./dev.db` (SQLite) |
| `AUTH_SECRET` | Секрет для подписи сессионного JWT | Заглушку **обязательно** заменить |
| `ADMIN_PASSWORD` | Пароль администратора для `db:seed` | `admin12345` (только для локальной разработки) |

Сгенерировать надёжный секрет:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Файл `.env` в репозиторий не попадает — он в `.gitignore`. Коммитится только
`.env.example` без значений.

## 7. Настройка базы данных

### SQLite (по умолчанию)

```bash
npm run db:push    # создаёт файл базы по схеме
npm run db:seed    # создаёт администратора
```

Файл базы — `prisma/dev.db`, в репозиторий не попадает.

### Переключение на PostgreSQL

1. В [`prisma/schema.prisma`](./prisma/schema.prisma) замените провайдер:

   ```prisma
   datasource db {
     provider = "postgresql"   // было "sqlite"
     url      = env("DATABASE_URL")
   }
   ```

2. В `.env` укажите строку подключения:

   ```bash
   DATABASE_URL="postgresql://user:password@localhost:5432/exam_preparation"
   ```

3. Примените схему:

   ```bash
   npm run db:push && npm run db:seed
   ```

Больше менять ничего не нужно: весь доступ к базе идёт через Prisma.

### Полезные команды

| Команда | Что делает |
|---|---|
| `npm run db:push` | Применить схему к базе |
| `npm run db:seed` | Создать администратора |
| `npm run db:reset` | Пересоздать базу с нуля и заполнить заново |
| `npx prisma studio` | Открыть визуальный просмотр базы |

### Учётная запись администратора

`db:seed` создаёт пользователя с ролью `admin`:

```text
логин:  admin
пароль: значение ADMIN_PASSWORD или admin12345
```

Если пароль оставлен по умолчанию, скрипт выводит предупреждение. Для любого
использования, кроме локальной разработки, задайте `ADMIN_PASSWORD`.

## 9. Среда выполнения кода

Код студента исполняется **по-настоящему**, а не сравнивается с эталоном
(требование раздела 14 ТЗ). Как это устроено:

### Изоляция

Код выполняется в `<iframe sandbox="allow-scripts">` **без**
`allow-same-origin`. Это даёт уникальный opaque-origin:

- нет доступа к cookie, `localStorage` и DOM приложения;
- нет доступа к файловой системе и системным командам (это браузер);
- сеть перекрыта заглушками до запуска кода студента: `fetch`,
  `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`;
- время выполнения ограничено — родительская страница уничтожает iframe.

Связь с приложением — только через `postMessage`.

### Почему всё локально

Браузеры блокируют загрузку подресурсов внутри opaque-origin iframe. Поэтому
библиотеки загружает **родительская** страница обычным запросом и передаёт их
внутрь строкой через `postMessage`. Побочный и полезный эффект: песочница
физически ничего не грузит из сети — и платформа целиком работает офлайн,
как и экзаменационный компьютер.

### Пять сред выполнения

| Среда | Что проверяет | Как устроена |
|---|---|---|
| `js` | Функции, алгоритмы, работа с данными | Прямое исполнение |
| `ts` | Типизация | Транспиляция компилятором TypeScript в родительской странице |
| `dom` | HTML, CSS, работа с DOM | Разметка студента рендерится в iframe |
| `react` | Компоненты | React 19 бандлится esbuild в `public/vendor/react` |
| `sql` | Запросы и схемы | SQLite на WebAssembly через sql.js |

### MySQL → SQLite

Студент учит MySQL — он будет на экзамене. В браузере доступен SQLite.
Различия переписывает слой совместимости
[`public/runner/sql-adapt.js`](./public/runner/sql-adapt.js), и **каждая замена
показывается студенту** в отчёте: `AUTO_INCREMENT → AUTOINCREMENT`,
`DATE_FORMAT → strftime` и так далее. Молча подменять диалект нельзя — иначе
складывается впечатление, что они одинаковы.

Отдельно стоит отметить два правила, которые чинят не различие диалектов,
а непонятные сообщения об ошибке:

- `INT PRIMARY KEY AUTO_INCREMENT` — в MySQL допустимы оба порядка слов,
  и раньше обратный давал невнятное «AUTOINCREMENT is only allowed on an
  INTEGER PRIMARY KEY» на совершенно правильном запросе;
- `DATEDIFF(конец, начало)` — в SQLite такой функции нет, переводится
  в разницу юлианских дней.

Слой покрыт тестами: [`tests/sql-adapt.test.ts`](./tests/sql-adapt.test.ts).

## 10. Запуск тестов

### Модульные и интеграционные (Vitest)

```bash
npm test              # один прогон
npm run test:watch    # в режиме наблюдения
```

| Файл | Что проверяет |
|---|---|
| `tests/grading.test.ts` | Баллы за задания, тесты и экзамен, штрафы за подсказки |
| `tests/progress.test.ts` | Прогресс, открытие материала, серии, слабые темы, готовность |
| `tests/srs.test.ts` | Интервальное повторение |
| `tests/recommend.test.ts` | Алгоритм рекомендаций |
| `tests/sql-adapt.test.ts` | Слой совместимости MySQL → SQLite |
| `tests/content.test.ts` | Целостность контента: ссылки, баллы, эталонные ответы |

`tests/content.test.ts` в том числе прогоняет каждый теоретический тест
эталонными ответами и требует ровно 100 % — опечатка в ключе ответа роняет сборку.

### Сценарные (Playwright)

```bash
npm run test:e2e                              # сценарии и адаптив
npm run test:solutions                        # эталонные решения всех заданий
npx playwright test --project=desktop         # основной сценарий
npx playwright test --project=mobile-390      # экран 390 × 844
npx playwright test --ui                      # с интерфейсом
```

Прогон решений вынесен в отдельную команду: он длится около десяти минут,
потому что открывает 210 заданий и по-настоящему исполняет код в песочнице.

Перед первым запуском:

```bash
npx playwright install chromium
```

| Файл | Что проверяет |
|---|---|
| `e2e/student-journey.spec.ts` | Весь путь: регистрация → план → теория → тест → код → результат → прогресс → проекты → демоэкзамен → генератор вариантов. Включая проверку, что песочница не пускает код в сеть, что в списках плана нет разметки программы и что поля дат стоят на одной линии |
| `e2e/audit.spec.ts` | Сетка по всем страницам: открывается, ровно один h1, нет ошибок в консоли и неудачных запросов, у изображений есть alt, у полей — подписи |
| `e2e/mobile.spec.ts` | Все страницы на 390 × 844: нет горизонтальной прокрутки, меню открывается, цели нажатия не мельче 32 px |
| `e2e/dark-theme.spec.ts` | Тёмная тема: палитра на месте, фон действительно тёмный, контраст текста не ниже требований WCAG AA |
| `e2e/task-solutions.spec.ts` | Эталонное решение каждого из 210 заданий прогоняется через настоящую песочницу и должно пройти все свои проверки. Запускается отдельно: `npm run test:solutions` |

Playwright сам поднимет сервер разработки. Если он уже запущен, переиспользует
его. Чтобы запретить запуск сервера: `E2E_NO_SERVER=1 npx playwright test`.

### Проверка контента

```bash
npm run content:check
```

Ловит то, что ломает платформу незаметно: ссылку на несуществующую тему,
дубликат идентификатора, расхождение баллов задания с суммой его тестов,
тест без пояснения, требование экзамена без чек-листа.

### Всё вместе перед коммитом

```bash
npm run typecheck && npm run lint && npm run content:check && npm test
```

## 12. Архитектура

### Контент отделён от логики

Учебный материал лежит в `content/**` как типизированные данные — ни одного
React-компонента. Это позволяет:

- проверять контент отдельно от приложения (`npm run content:check`);
- находить битые связи компилятором, а не в рантайме;
- править материал, не трогая код.

### Слой правок из админки

```text
content/**  (файлы, под контролем версий)
     ↓
ContentOverride  (таблица в базе, правки из админки)
     ↓
lib/content.ts   (объединяет одно с другим)
     ↓
страницы
```

Админка пишет правки в базу, а не в файлы: пересборка не требуется, а исходный
материал остаётся неизменным и восстановимым. Каждая правка проверяется схемой
Zod до сохранения.

### Логика оценивания — чистые функции

`lib/grading`, `lib/progress`, `lib/srs`, `lib/recommend` не обращаются к базе.
На вход — снимок состояния, на выход — результат. Отсюда 136 модульных тестов,
которые проходят за секунду и не требуют поднятого приложения.

Сервисы (`lib/progress/service.ts`, `lib/exam/service.ts`) занимаются базой и
вызывают эти функции.

### Вход в систему

Сессия — JWT в cookie: `httpOnly`, `sameSite=lax`, подпись `AUTH_SECRET`.
Пароли — bcrypt. Сделано намеренно тем же способом, который студент будет
писать на экзамене: исходный код платформы можно читать как пример.

### Рендеринг markdown

Учебные тексты написаны в markdown. Рендерит их собственный модуль
[`lib/markdown.tsx`](./lib/markdown.tsx), который возвращает React-элементы и
**не использует** `dangerouslySetInnerHTML`. Причина простая: платформа учит
не превращать пользовательский текст в разметку — странно было бы нарушать
это правило у себя.

### Ограничения по замыслу

- База по умолчанию SQLite: запуск без установки СУБД и работа офлайн.
- Выполнение кода только в браузере: серверная песочница потребовала бы
  Docker и постоянно работающего сервера.
- Все библиотеки локальные: экзаменационный компьютер без интернета.

## 13. Инструкции для администратора

### Вход в админку

1. Войдите под учётной записью с ролью `admin` (создаётся `npm run db:seed`).
2. Ссылка «Админка» появится в боковом меню, адрес — `/admin`.

### Что можно делать

| Раздел | Возможности |
|---|---|
| Темы | Править заголовок, суть, теорию, примеры, ошибки, связи |
| Задания | Править условие, требования, заготовку кода, тесты, подсказки, разбор |
| Тесты | Править вопросы, варианты, правильные ответы, пояснения |
| Мини-проекты | Править ТЗ, требования, ограничения, чек-лист |
| Экзамены | Править состав модулей и чек-листы |

### Как работает правка

1. Админка показывает объект в виде JSON с подсветкой.
2. При сохранении данные проверяются схемой Zod. Ошибки выводятся списком
   с указанием поля — сохранить некорректный объект нельзя.
3. Проверенная правка пишется в таблицу `ContentOverride`.
4. Страницы начинают отдавать изменённую версию сразу, без пересборки.

### Как откатить правку

В карточке объекта — кнопка «Вернуть исходный вариант». Она удаляет запись из
`ContentOverride`, и платформа снова отдаёт версию из файлов.

### Смена пароля администратора

```bash
ADMIN_PASSWORD="новый-длинный-пароль" npm run db:seed
```

Скрипт обновит пароль существующей учётной записи.

### Резервная копия

Пользовательские данные и правки живут только в базе:

```bash
# SQLite
cp prisma/dev.db prisma/dev.backup.db

# PostgreSQL
pg_dump exam_preparation > backup.sql
```

Контент из `content/**` резервировать не нужно — он под контролем версий.

## 13a. Как поправить описание дня плана

У каждого из 210 дней есть **два** текста:

| Текст | Где лежит | Можно ли менять |
|---|---|---|
| Дословный из программы | `content/curriculum/plan.generated.json` | Нет. Это разбор исходного файла программы: правится сам файл, затем `node scripts/parse-plan.mjs` |
| Человеческое объяснение | `content/curriculum/day-notes.ts` | Да, это текст платформы |

Формулировка программы написана телеграфно и для того, кто уже в теме:
«Flexbox: `display: flex`, `justify-content`, `align-items`». Новичку такая
строка ничего не объясняет. Поэтому платформа показывает своё объяснение
первым, а формулировку программы — рядом, под раскрывающимся блоком.
Подменять одно другим нельзя: студент должен видеть и то, что написано
в программе, и что это значит.

```ts
'day-03-1': {
  title: 'Раскладка в ряд: Flexbox',        // короткое имя, не список терминов
  theory:
    'Flexbox — способ расставить элементы в линию и управлять расстояниями ' +
    'между ними. Разбираемся, как прижать одно к левому краю, другое к правому.',
  practice: 'Собираем шапку сайта: логотип слева, меню справа.',
  why: 'Зачем это на экзамене — только там, где связь неочевидна.',
},
```

Правила, которые проверяются тестами:

- объяснение есть у **каждого** дня — пропуск роняет `npm run content:check`;
- в объяснении нет кода в обратных кавычках: если он остался, текст просто
  скопировали из программы вместо того, чтобы переписать;
- заголовок короче 60 символов;
- объяснение не совпадает дословно с текстом программы.

Объяснение показывается везде, где день попадается студенту: на дашборде
в карточке «Сегодня», в списке дней недели и на странице дня. Дословная
формулировка живёт только на странице дня, под раскрывающимся блоком.
Сценарный тест `4c` проверяет, что в списках не появилось обратных кавычек —
это верный признак, что где-то снова выводится текст программы.

## 13b. Даты: договорённость о часовом поясе

Календарные даты (начало подготовки, дата демоэкзамена) хранятся как
**полночь по местному времени**: `new Date('2026-09-14T00:00:00')`. В UTC+3
это `2026-09-13T21:00:00Z` — то есть в UTC там предыдущие сутки.

Отсюда правило: обратно в строку `ГГГГ-ММ-ДД` такую дату переводят только
через `dateKey()` из `lib/utils.ts`, который читает местные `getFullYear`,
`getMonth`, `getDate`.

```ts
dateKey(date)                      // 2026-09-14 — календарный день
date.toISOString().slice(0, 10)    // 2026-09-13 — день по UTC, не тот
```

`toISOString()` уместен только для моментов времени: когда начата попытка
экзамена, когда отправлено решение. Для календарной даты он даёт сдвиг на
сутки восточнее Гринвича, а если такую дату показать в поле формы, то
следующее «Сохранить» запишет сдвиг обратно в базу.

## 14. Как добавить тему

Темы лежат в `content/topics/month-NN.ts`.

### Шаг 1. Добавить объект темы

```ts
{
  id: 'css-container-queries',          // уникальный, латиницей через дефис
  title: 'Контейнерные запросы',
  tech: ['css'],
  monthNo: 1,
  weekNo: 3,
  importance: 'extra',                  // core | extra
  summary: 'Одно-два предложения: в чём суть и зачем это на экзамене.',
  mustKnow: ['Пункт 1', 'Пункт 2'],     // 3–5 пунктов
  theory: `## Заголовок

Текст в markdown: таблицы, списки, блоки кода.`,
  examples: [
    {
      title: 'Название примера',
      language: 'css',
      code: '.card { container-type: inline-size }',
      explanation: 'Почему именно так.',
    },
  ],
  mistakes: [
    { title: 'Что делают не так', why: 'К чему это приводит.' },
  ],
  quizId: 'quiz-css-container-queries', // тест создаётся отдельно
  taskIds: [],
  resources: [],
  examRefs: [],                         // идентификаторы требований экзамена
  prerequisites: ['css-responsive'],    // темы, которые должны быть пройдены
  estimatedMinutes: 30,
  planDays: ['day-03-4'],               // дни программы
  source: 'extra',                      // plan | exam | docs | author
}
```

### Шаг 2. Проверить

```bash
npm run content:check && npm run typecheck
```

Валидатор проверит: уникальность идентификатора, существование
`prerequisites`, `examRefs`, `planDays`, наличие теории и разбора ошибок.

### Что важно

- **`source` обязателен и должен быть честным.** `plan` — материал из учебной
  программы, `exam` — из задания демоэкзамена, `docs` — из документации
  технологии, `author` — добавлено разработчиком платформы. По этой метке
  студент понимает, откуда взялось требование.
- **`prerequisites` не должны образовывать цикл** — это проверяется тестом.
- **Новая тема без теста даст предупреждение**, но не ошибку: тест можно
  добавить следующим шагом.

## 15. Как добавить практическое задание

Задания лежат в `content/tasks/`:

| Файл | Что внутри |
|---|---|
| `month-NN.ts`, `month-NN-css.ts`, `month-NN-js.ts` и подобные | Задания месяца по темам |
| `month-NN-daily.ts` | Задания для дней месяца, у которых практики не было |
| `week-assembly-mN.ts` | Сборки седьмых дней: задание на всё, что было за неделю |
| `week-assembly.ts` | Собирает сборки всех месяцев в один список |

Новое задание добавляют в тот файл, к которому оно ближе по смыслу, и
подключают в `content/tasks/index.ts`.

### Шаг 1. Выбрать среду выполнения

| Среда | Когда использовать |
|---|---|
| `js` | Функции, алгоритмы, обработка данных |
| `ts` | Когда проверяется именно типизация |
| `dom` | Разметка, стили, работа с DOM |
| `react` | Компоненты |
| `sql` | Схемы и запросы |

### Шаг 2. Написать задание

```ts
{
  id: 'task-css-container',
  title: 'Карточка, реагирующая на ширину контейнера',
  kind: 'function',       // function | fix-bug | find-bug | complete | output | api | db | files | app
  runtime: 'dom',
  difficulty: 3,          // 1…5
  tech: ['css'],
  topicIds: ['css-container-queries'],
  monthNo: 1,
  weekNo: 3,
  statement: `Условие в markdown. Требования — списком, без недосказанностей.`,
  requirements: ['Требование 1', 'Требование 2'],
  starterCode: `<style>\n  /* ваш код */\n</style>`,
  viewport: { width: 390, height: 844 },   // для заданий на адаптив
  tests: [ /* см. шаг 3 */ ],
  hints: [
    { level: 1, text: 'Направление мысли.', penaltyPercent: 10 },
    { level: 2, text: 'Часть алгоритма.', penaltyPercent: 25 },
    { level: 3, text: 'Почти готовая структура.', penaltyPercent: 40 },
  ],
  solution: `Полный код решения.`,
  solutionExplanation: `Разбор: почему так, а не иначе, и где обычно ошибаются.`,
  maxScore: 12,           // ОБЯЗАТЕЛЬНО равен сумме points всех тестов
  estimatedMinutes: 20,
  examRefs: ['m2-mobile'],
  planDays: ['day-03-4'],
  source: 'extra',
}
```

### Шаг 3. Написать тесты

Тесты — настоящие проверки исполнения. Доступные типы:

```ts
// Вызов функции с аргументами
{ id: 't1', name: 'Понятное название', type: 'call',
  entry: 'checkLogin', args: ['ivanov26'], expected: true, points: 3 }

// Вычисление выражения в области видимости решения
{ id: 't2', name: '…', type: 'expr', expression: 'items.length', expected: 4 }

// Произвольная проверка: ctx.get, ctx.assert, ctx.source
{ id: 't3', name: '…', type: 'assert', code: `
const result = ctx.get('validate')({ login: '' });
ctx.assert(Boolean(result.login), 'Пустой логин должен попасть в ошибки');
`, points: 4 }

// Проверка отрисованного документа: ctx.$, ctx.$$, ctx.css, ctx.text, ctx.wait
{ id: 't4', name: '…', type: 'dom', code: `
ctx.assert(ctx.$('header'), 'Нужен тег header');
`, points: 2 }

// Проверка React-компонента: ctx.render, ctx.click, ctx.change, ctx.submit, ctx.wait
{ id: 't5', name: '…', type: 'react', code: `
return ctx.render('Menu', { user: null }).then(() => {
  ctx.assert(ctx.$('[data-testid="login"]'), 'Гость должен видеть вход');
});
`, points: 4 }

// SQL: контрольный запрос и ожидаемая таблица
{ id: 't6', name: '…', type: 'sql-query',
  check: 'SELECT title FROM statuses ORDER BY id',
  expectedColumns: ['title'],
  expectedRows: [['Новая'], ['Мероприятие назначено']],
  ordered: true, points: 5 }

// SQL: структура таблицы и внешние ключи
{ id: 't7', name: '…', type: 'sql-schema', table: 'applications',
  columns: [{ name: 'id', pk: true }, { name: 'user_id', notNull: true }],
  foreignKeys: [{ column: 'user_id', refTable: 'users' }], points: 4 }
```

Тест можно пометить `hidden: true` — тогда студент увидит его название и
результат, но не ожидаемое значение.

### Шаг 4. Привязать к дню плана

Поле `planDays` связывает задание с днями учебного плана:

```ts
planDays: ['day-03-2'],
```

**У каждого из 210 дней должно быть хотя бы одно задание** — это проверяет
`npm run content:check` и модульные тесты. Правило не формальное: день без
практики превращается в чтение, а платформа существует ради того, чтобы
студент писал код каждый день.

### Шаг 5. Проверить

```bash
npm run content:check && npm run typecheck && npm test
npm run test:solutions      # прогон эталонного решения через песочницу
```

Последняя команда — главная. Она берёт `solution` каждого задания, вставляет
в редактор и прогоняет все его проверки по-настоящему. Без неё задание
с опечаткой в тесте выглядит целым ровно до того момента, когда студент
потратит на него полчаса.

### Правила, которые стоит соблюдать

- **`maxScore` = сумма `points` всех тестов.** Иначе прогресс будет врать —
  это проверяется и валидатором, и тестами.
- **`solution` — полный работающий код, а не фрагмент.** Студент открывает
  разбор, чтобы вставить его и запустить; кроме того, по нему работает
  `npm run test:solutions`. Для `dom`-задания это весь документ вместе
  с разметкой, для `js` — все объявления, включая данные из заготовки.
- **Три уровня подсказок**, штраф растёт с уровнем.
- **`solutionExplanation` объясняет «почему», а не пересказывает код.**
  Это главная обучающая часть задания.
- **SQL-заданию нужен `setupSql`**, кроме заданий вида «спроектируйте схему».

### Ловушка: проверки одного задания идут по одному документу

Все проверки задания выполняются подряд **без пересоздания** страницы или
React-компонента. Состояние переезжает из проверки в проверку: если первая
кликнула по кнопке, вторая увидит уже переключённое состояние, а `useState`
сохранит значение из предыдущего `ctx.render`.

Поэтому проверки пишут так, чтобы они не зависели от порядка:

```ts
// Плохо: рассчитывает на нетронутый компонент
ctx.click('#next');
ctx.assert(activeIndex() === 1, '…');

// Хорошо: сравнивает с тем, что есть сейчас
const before = activeIndex();
ctx.click('#next');
ctx.assert(activeIndex() === (before + 1) % 4, '…');
```

Второй приём — привести состояние к известному прямо в проверке:

```ts
if (ctx.css(ctx.$('#filters'), 'display') !== 'none') ctx.click('#toggle');
```

### Ловушка: анимации в фоновой вкладке

Браузер притормаживает CSS-анимации, когда вкладка не на виду, поэтому
проверка «подождать 700 мс и посмотреть на `opacity`» проходит не всегда.
Проверяйте объявление, а не проигрывание: `animation-name`,
`animation-duration`, `animation-fill-mode`.

## 16. Как добавить теоретический тест

Тесты лежат в `content/quizzes/month-NN.ts`.

```ts
{
  id: 'quiz-css-container-queries',
  title: 'Контейнерные запросы',
  topicIds: ['css-container-queries'],
  tech: ['css'],
  monthNo: 1,
  difficulty: 2,
  passPercent: 70,        // 80 для тем с дословными требованиями экзамена
  examRefs: ['m2-mobile'],
  questions: [
    {
      id: 'q1',
      type: 'single',
      text: 'Вопрос?',
      options: [
        { id: 'a', text: 'Вариант' },
        { id: 'b', text: 'Другой' },
      ],
      correct: 'b',
      explanation: 'Почему верен этот вариант и чем плохи остальные.',
    },
    { id: 'q2', type: 'boolean', text: 'Утверждение.', correct: true, explanation: '…' },
    { id: 'q3', type: 'multiple', text: '…', options: [/* … */], correct: ['a', 'c'], explanation: '…' },
    { id: 'q4', type: 'match', text: '…', left: [/* … */], right: [/* … */],
      correct: { l1: 'r1', l2: 'r2' }, explanation: '…' },
    { id: 'q5', type: 'order', text: '…', items: [/* … */],
      correct: ['i1', 'i2', 'i3'], explanation: '…' },
    { id: 'q6', type: 'text', text: '…', correct: ['break'],
      caseSensitive: false, explanation: '…' },
  ],
}
```

### Правила

- **Пояснение обязательно у каждого вопроса.** Тест без пояснений не учит —
  это проверяется тестами.
- **`caseSensitive: true`** — только для значений, которые на экзамене
  проверяют дословно (`Admin26`, `Demo20`). По умолчанию сравнение мягкое:
  без учёта регистра, пробелов и пунктуации, «ё» = «е».
- **Правильный ответ должен быть из списка вариантов** — проверяется валидатором.
- **Эталонные ответы прогоняются тестом** и обязаны дать 100 %.

## 17. Как добавить мини-проект

Проекты лежат в [`content/projects/projects.ts`](./content/projects/projects.ts).

```ts
{
  id: 'project-08-something',
  title: 'Название',
  goal: 'Одно предложение: что студент научится делать.',
  monthNo: 3,
  difficulty: 4,          // не ниже, чем у проекта предыдущего месяца
  tech: ['react'],
  topicIds: ['react-state'],
  examRefs: ['m2-cabinet-ux'],
  brief: `## Что делаем\n\nТехническое задание в markdown.`,
  requirements: ['Требование 1', 'Требование 2'],
  constraints: ['Без внешних библиотек'],
  checklist: [
    { id: 'c1', text: 'Пункт', weight: 3, verification: 'auto' },
    { id: 'c2', text: 'Пункт для самопроверки', weight: 2, verification: 'manual' },
  ],
  hints: [ /* три уровня */ ],
  resources: [],
  autoCheck: {            // необязательно
    runtime: 'react',
    maxScore: 20,         // = сумма points тестов
    starterCode: '…',
    tests: [ /* как у заданий */ ],
  },
  estimatedHours: 4,
  planDays: ['day-12-6'],
  source: 'author',
}
```

### Правила

- **Сложность не должна падать** от месяца к месяцу — это проверяется тестом.
- **В чек-листе обязан быть хотя бы один ручной пункт.** Проект без ручной
  части означал бы, что платформа проверяет всё сама — а это неправда.
- **`autoCheck` необязателен.** Для проектов вроде «прогон модуля 1 за
  90 минут» автопроверки нет вовсе, и честнее так и сказать.

## 18. Как добавить экзаменационный вариант

### Официальный вариант

[`content/exams/demo.ts`](./content/exams/demo.ts) содержит вариант № 2
демоэкзамена 2026 года. **Его тексты — дословные цитаты из PDF.** Менять их
нельзя: на этом держится ценность режима. Если появится новый официальный
вариант, добавляйте его туда же с `kind: 'demo'` и `source: 'exam'`.

### Тренировочный вариант

Добавляется в [`content/exams/practice.ts`](./content/exams/practice.ts):

```ts
{
  id: 'exam-practice-delivery',
  title: 'Тренировочный вариант — «Доставка еды»',
  kind: 'practice',
  level: 'exam',
  domain: 'Служба доставки',
  source: 'author',                       // обязательно author
  sourceNote: 'Вариант составлен разработчиком платформы. Официальное задание — только вариант № 2.',
  description: `Чем этот вариант отличается и на что смотреть.`,
  totalMinutes: 240,                      // = сумма minutes модулей
  examRefs: ['m1-db', 'm1-register'],
  modules: [
    {
      id: 'practice-delivery-m1',
      moduleNo: 1,
      title: 'Проектирование и разработка',
      minutes: 90,
      instruction: `**Задание составлено разработчиком платформы.**\n\n…`,
      tasks: [
        { id: '…', kind: 'code', taskId: 'task-sql-schema', points: 8, title: '…' },
        {
          id: '…',
          kind: 'checklist',
          title: 'Чек-лист модуля 1',
          description: 'Эти пункты проверяются в вашем проекте.',
          points: 20,                     // = сумма points пунктов
          items: [{ id: 'c1', text: 'Пункт', points: 2 }],
        },
      ],
    },
    /* модули 2 и 3 */
  ],
}
```

### Обязательные правила

- **`source: 'author'` и честный `sourceNote`.** Тренировочный вариант нельзя
  выдавать за официальный — это прямое требование раздела 46 ТЗ, и оно
  проверяется тестом.
- **Три модуля, 90 + 90 + 60 минут**, сумма — 240.
- **В каждом модуле и автопроверяемые задания, и чек-лист.**
- **`points` чек-листа = сумма `points` его пунктов.**
- **Не копируйте дословные формулировки официального задания** в инструкции
  тренировочного варианта. Цитаты уместны только в пунктах чек-листа, где
  прямо отмечено, что это требование настоящего экзамена.

## 19. Чего платформа не делает

Сказано прямо, чтобы не возникало ложных ожиданий:

- **Не заменяет экзамен.** Настоящий демоэкзамен — четыре часа в VS Code с
  сервером, базой и Git. Платформа тренирует части этой работы и даёт
  чек-листы для остального.
- **Не предсказывает оценку.** Процент готовности — внутренняя метрика
  платформы. Официальной шкалы в задании нет, и веса требований —
  обоснованное решение разработчика, а не документ.
- **Не проверяет ваш проект.** ER-диаграмму, коммиты и внешний вид приложения
  в вашем репозитории отмечаете вы сами. Платформа не делает вид, что может
  это проверить.
- **Не выдумывает содержание экзамена.** Официальный вариант один — вариант
  № 2 из PDF. Всё остальное помечено как авторское.
